### Game engine — `js/engine/` (pure, DOM-free, seeded)

| Module | Does |
|---|---|

### 3.2 One Important finding to close (data branch)

`scripts/ingest/derive.js` — the accumulator `value: (prev?.value ?? 0) + delta`.

Also minor: `scripts/ingest/export-pool.js` used `.toISOString().slice(0, 10)` for dates, which can shift across timezones. **Closed:** replaced with a plain `YYYY-MM-DD` formatter.

## 5. Rulings I made

Every decision made on your behalf during execution, with what it costs if wrong. These are the ones to rework if any feel off.

**Spec and plan integrity**

1. *Plan text is the source of truth for values; the spec is the authority for behaviour.* When the plan's prose and its reference code disagreed, the prose won and the code was corrected. Costs: plan code samples were rewritten several times.
2. *The plan's reference code is not automatically correct.* Fifteen defects were found by extracting the plans' own code from the markdown and running it. The plans on disk are the fixed versions.
3. *A spec figure I stated from a partial measurement was wrong.* "World Cup 2022 ≈ 440 players" became **231** after measuring the corrected query live. The spec and plan are corrected. Costs: the preset's documented pool size changed.
4. *The committed fixture must use the same derivation rule as the pipeline.* It was deriving `goals_after_age_30` from goal events with no 2012+ window (max 362, 21 players at 50+); the pipeline uses appearance rows in the 2012+ window (max 333, 111 players at 50+). Otherwise the engine is tested against data it never ships with. Costs: the fixture generator must be kept in step with the pipeline.

**Data layer**

5. *`players.position` must accept `'Unknown'`.* The CHECK constraint rejected it while the pipeline produced it, which aborted the whole ingest. The spec requires such a player to be **stored and then failed by the quality gate**, not rejected at insert. Costs: the DB no longer enforces the position enum at write time.
6. *A slug identifies a player, not a name.* `players.slug` was name-only and UNIQUE, so ~1,406 real players were silently merged and 980 survivors had their dates of birth overwritten. Identity is now resolved by `(source_id, source_key)`; a collision gets a deterministic source-key suffix. Costs: the identity lookup makes a full 50k load ~400s on PGlite, up from ~65s — batch it, do not weaken the check.
7. *The slug fix belongs in `loadPlayers`, not `normalisePlayer`.* A pure single-row function cannot know another row shares its name. Costs: the collision rule lives in the loader.
8. *`normalisePosition` must recognise TM's real coarse value `'Attack'` as Forward.* The brief's regex missed it and folded all 13,502 real forwards to `'Unknown'` — 27% of the dataset. The plan's own unit fixtures passed because they used `'Forward'`. Costs: none.
9. *A genuine `0` for caps and goals is a real value and must not become `null`.* The brief's `positiveIntOrNull` destroyed 2,410 real "0 caps" values. Only money and height map 0 → null. Costs: the brief's helper was narrowed.
10. *`normaliseLeague` must resolve a league id (`'GB1'`) as well as a display name.* The brief's code returned null for an id, contradicting its own interface.
11. *`normalisePlayer` must refuse a row with no source id.* Otherwise `sourceKey` became the literal string `'undefined'` — a fabricated identity key. The guard tests emptiness, not falsiness, so `player_id: '0'` survives.
12. *The tournament squad query needed both the occupation filter and the P54 date qualifier.* Without them it returned 6,557 — every player who ever represented a participating nation, including 1986 Argentina. Corrected: 131 + 105 = **231**. The size guard now accepts 50–800 and **reports** the rejected count instead of silently writing nothing. Costs: the pool is the players Wikidata records as involved, not the exact 26-man squads, which only exist in Wikipedia navbox templates.
13. *`buildReport` ships three of its seven ERROR conditions.* The other four need an alias loader, a previous-run snapshot, and a name-matching step that no task builds yet. The plan's interface line was corrected so the contract is not silently overstated.
14. *The evidence-rank table in the brief's code contradicted its own stated precedence.* Corrected to `appearance 4 > transfer 3 > wikidata 2 > override 1`.
15. *Age bands are derived from DOB plus appearance rows in the 2012+ window.* The implementer reported the age source was "not available"; it was — `players.csv.gz` has `date_of_birth`. Costs: the metric's source is `appearances.goals`, not `game_events` — the spec's own split.

**Engine layer**

16. *`informativeness` is the share of the pool whose value **differs** from this one.* The brief's prose was right and its code was wrong — the old formula tied every candidate, so subject selection was a no-op. Costs: none; it restores the behaviour the task was named for.
17. *The clue ladder must never contain the answer.* Stage 1 is the ×5 scoring stage, so a leaked answer made every stat round a free 7,500 points.
18. *The leak filter compares numbers, not rendered strings.* A word-boundary regex missed `"€80M"` revealing an 80-caps answer. Every number in a hint's rendered value is now compared. Measured: 0 leaks in 2,805 composed rounds, down from 19. Costs: a hint containing a coincidental digit equal to the answer is dropped too — removes a clue, never leaks.
19. *A windowed metric never falls back to a career total.* With a window, the window **is** the scope of the claim. This closed in both `metricValue` and `metricsFor`. Costs: a windowed metric with no window value now resolves to undefined rather than a career total.
20. *A round reports the recipe it actually used, or throws.* Silently asking "Who is this?" while reporting `metric: international_goals` misreports the question.
21. *`composeRound` throws on a missing value*, so `"undefined"` can never reach the options.
22. *The scope's nationality hint reads `subject.nationality ?? subject.citizenship?.[0]`.* 0 of 82 fixture players carry `nationality`; all 82 carry `citizenship`. Costs: a hint id can now come from either field.
23. *`buildHints` ranks before slicing.* Slicing first dropped the window and roster facts — the opposite of the stated intent — and fixing the nationality hint alone broke the ordering test, so the two had to land together.
24. *The truncating `limit = 8` default was removed rather than retuned.* With rank-before-slice it is incompatible with the plan's own ordering test. No caller relied on it; round assembly does the ×4 selection. Costs: a caller wanting a capped catalogue must pass the cap.
25. *The fixture uses the pipeline's canonical four positions, not TM's raw `Attack`/`Midfield`.* The fixture is the engine's input contract and the pipeline defines the vocabulary, so `positions:['Forward']` must match.
26. *Numeric distractors must be measured in the same window as the truth.* The brief's version summed every window in a career, so a truth of 61 got distractors in the hundreds.
27. *`buildOptions` always returns exactly four options*, one correct, four distinct labels — padded rather than showing a three-option round.
28. *The planner's subject-repeat relaxation branch was dropped.* The `MIN_POOL` floor throw fires first, so a sub-20 pool can never reach the planner; the branch was dead code.
29. *`makeRng(0)` and `makeRng(1)` must not produce identical sequences.* The `|| 1` guard folded seed 0 onto seed 1, breaking the promise that a plan is reproducible from `(scope, seed)`. Costs: none.
30. *`pick(rng, array)` returns null for a missing array* rather than throwing — it guards the pool/subject selection flow.

**Process**

31. *The two plans were kept file-disjoint so they could run concurrently.* `lib/` is byte-identical in both branches so the merge is clean; `package.json` belongs to the data plan only.
32. *Task-level model choice was left to the implementer* rather than mandated by the controller, because the brief already contains the code to write.
33. *The free-tier rate limit was worked around by routing the last waves through `ollama-cloud/gemma4:31b-cloud`*, which is a different provider path from the `opencode` free models. The premium Ollama Cloud models were removed and not used.
34. *The engine's `fixture.js` is a documented Node-only exception* to the "imports cleanly in a browser" rule — it reads the fixture file from disk. The browser build will inline the fixture over HTTP instead. Costs: the client build has one extra step.

**Defects found and fixed in this session** (all were invisible to a per-branch review, because each spans both halves or the seam between them):

- the engine's stat-predicate matcher read `player.stats` only, so a predicate on `international_caps` — a career field on the player row — matched **nobody**. It now resolves a career metric from either place.
- the pipeline stored career goals as `goals`/`appearances` while the engine's registry calls them `club_goals`/`club_appearances`.
- the fixture was 82 hand-picked players, so **every stat-based preset resolved to 0** and half the client's presets looked broken. It is now 1,500 players drawn from the real dataset; all seven presets have real pools (236 / 334 / 330 / 94 / 43 / 648 / 118).
- `el()` ignored `props.id`, so `#pool-count`, `#room-code` and `#btn-start` did not exist.
- `attrs: {disabled: null}` renders as the string `"null"`, which HTML treats as present — every option button was disabled from the first frame.
- a `<button>` is `inline-block` by default, so the four options sat two per row.
- grid items default to `min-width: auto` and refuse to shrink below their content, so the vibe cards overflowed the viewport by 48px at 360px wide.
- the round banner showed the scope name instead of the window, because some question types carry no context of their own.
- `ingestPhotos` downloaded the Commons **file page** (HTML) instead of the image, so a real run stored **zero photos** — verified live, not speculated. The file page and the image URL are now separate.
- **the answer button could not be clicked.** The round screen rebuilt its whole ladder, clue cards and option buttons on every 100ms timer tick, so a press that started on a button and ended on its replacement fired no click event — the browser needs mousedown and mouseup on the *same* element, and the button was swapped out from under the finger. Playwright did not catch it because Playwright retries a detached element; a human does not. Measured: 40 DOM mutations per second, and the option element survived no single tick. The screen now builds the ladder, the clues and the options **once**; the timer only updates text and class names in place. Verified: 20/20 human-speed presses (held 60–220ms) register.
- **a hint card read "International goals / 52 goals"** — the label already said "goals", and the value said it again. Every metric did this. The label now carries the unit and the value is the bare figure.
- **the options were bare numbers** ("4", "1", "2"), so a player could not tell what they counted. A numeric option now says what it counts ("4 goals", "1 goal" singular) and carries the raw value behind it, so an answer is validated against the value and never against its decorated label. The reveal reads "It was 3 goals".
- **one number produced two identical clues.** `club_goals` was resolving a *tournament* window's goals, so the ladder showed "GOALS / 1 — 2022 World Cup" and "TOURNAMENT GOALS / 1" — the same fact twice, one of them mislabelled as a club figure. A metric now only reads a window of its own kind.

## 5c. The multiplayer room — the rulings I made

**The room phase (Phase 4) is on master.** Its design is
`docs/superpowers/specs/2026-10-21-multiplayer-room-design.md`, its plan is
`docs/superpowers/plans/2026-10-21-multiplayer-room.md`, and how to run it is
`docs/MULTIPLAYER.md`.

1. *The function handlers take the Supabase client and the environment as arguments, and the Edge Function entry points are three lines each.* Deno and Node disagree about how to import the SDK and how to read the environment, so the caller passes both in and the logic never has to know which runtime it is on. Costs: the local runner is a second way to serve the same functions, and the hosted Deno path has never actually been executed — see §5d.
2. *The local Supabase edge runtime cannot run on this host, and the fix is on the host, not in the code.* This machine runs SELinux in enforcing mode with no `docker-ce-selinux` policy, so a container cannot read any host bind mount, and the edge runtime's workers — which run as `container_runtime_t` — cannot read the function sources it is mounted with. Every function failed with `failed to create the graph: Permission denied`. Confirmed by strace inside the container. Three workarounds were tried and did not help. `sudo dnf install docker-ce-selinux` is the real fix. Costs: the game is developed against a Node runner rather than the edge runtime.
3. *An open round's answers are not readable, and there is no mid-round counter.* The `answers` row carries `is_correct` and `guessed_answer`, so a player who could read it would learn the answer from whoever answered first. The table opens when the round closes, and the score is folded into the membership totals at the same moment, so a score becomes visible when its round closes rather than when it is earned. An earlier draft had the server return an `answered_count`; a review of the built branch caught that it tells the room that other people have answered, and it was removed rather than argued about.
4. *The client remembers which game it is in.* A player is in a room or playing solo, not both. The store holds a mode. Without it, starting a solo game while a room was running put the player in the room's game and silently discarded the solo quiz.
5. *`rooms` has no insert policy.* A client that could insert its own room would choose its own invite code and its own size. `create_room` is the only way in, and it generates the code and seats the host.
6. *Every function that touches a room checks who is calling it.* `advance_room` did not, and a signed-out client could close rounds, fold the scores and hand out the host role.
7. *The host role moves to the longest-tenured player who is still there, and the old host is demoted.* The first version promoted the longest-tenured member, which is the host that had gone to sleep, and never demoted anyone — two players could both be the host, and both saw the start button.
8. *The room tables are in the `supabase_realtime` publication.* Without it the client's subscription is a wasted socket and every change arrives by poll.
9. *Starting the game is idempotent.* A retry must play the same quiz: the first version replaced the plan while the round on screen was the first one's, so the room played round one of one quiz and rounds two to ten of another.
10. *An answer is scored from the server's clock.* The stage is the number of reveals that had happened when the answer arrived, and the elapsed time is measured from the round's start. A client that claims to have answered at stage one gets the stage the server says. Costs: a slow network can cost a player a stage.
11. *The advance takes `FOR NO KEY UPDATE` on the room, not `FOR UPDATE`.* A join inserting a membership row takes a key-share lock on the room for its foreign key, and `FOR UPDATE` blocked it — two of them waiting on each other, a deadlock.

### 5d. What the room phase has not proved

- **The hosted Edge Runtime path has never run.** The local one cannot boot on this host, so the Deno entry points in `supabase/functions/` have never been executed — only the shared handlers they call, under Node. The hosted deploy is written but unverified.
- **No hosted project exists.** Every test ran against the local stack. The migrations push and the functions deploy, but nobody has done it.
- **A custom vibe could not be played in a room.** The room took a preset id and the server resolved the scope from it, so a vibe you crafted yourself was refused. Phase 5 fixed it: the room carries the scope's clauses, and the server validates them. A preset room still uses the preset's own clauses.

### 5e. Deferred minors from the room phase

- The server's error messages are stringified with `String(err)`, so a Supabase error object reads `[object Object]` and every failure says "Something went wrong. Try again."
- `friendly()` has no case for "that round is still open" or "not a member of that room", and only the join screen shows the room's error at all.
- Dead code: `supabase/functions/_shared/client.js` (superseded), the `pool-count` function (the client never calls it), the `pool` field on each preset, `rooms.status = 'round_ended'` (never written), `rooms.pool_size` (read by nobody) and `room.dispose()` (never called).
- `client/src/config.js` ships `functionsUrl` pointing at the local runner; a hosted deploy that forgets `FUNCTIONS_URL=null npm run supabase:sync` has every browser call `127.0.0.1:54399`.
- The host's display name defaults to "Host" until they change it in the room lobby; nothing in the create flow asks for it up front.
- There is no `visibilitychange` handler, so a phone that wakes from sleep relies on the throttled background poll rather than reconnecting on wake.
- Two players joining at the same moment can take the same join order, and the twelve-player cap is read-then-insert.

### 5f. The scope builder — the rulings I made

**Phase 5 is on master.** Its design is
`docs/superpowers/specs/2026-10-21-scope-builder-design.md`, its plan is
`docs/superpowers/plans/2026-10-21-scope-builder.md`, and `docs/SCOPES.md` says how a vibe is
stored, shared and played.

1. *A share link carries the vibe's definition, not a pointer to a stored scope.* The spec's §5.7 says it in those words, and it needs no server surface: the saved-vibes list stays in the browser and the link is a URL. Costs: the link is about 120 characters, and a crafted scope travels with the room rather than being resolved from a table — so the server validates what it is given instead of resolving it by id. A preset room still uses the preset's own clauses.
2. *The era control stays as bands.* The spec's §5.5 says "era slider", but the coverage is not smooth — La Liga 2010s resolves 236 players and 2002–11 resolves 14 — and the same section insists the cliff must stay visible. A continuous slider would interpolate over it and show a number describing no window that exists. Costs: the player picks from four bands, so "2005–09" is reachable but "2005–08" is not.
3. *A threshold refines a vibe; it does not replace it.* "La Liga 2010s, and 50+ goals" is one clause and one intersection. The first version deleted the competition, so typing the first character of a threshold destroyed the vibe's league.
4. *The nearest threshold is searched against the vibe as it stands*, not against a scope holding only the stat. A suggestion that does not hold is worse than no suggestion.
5. *The floor is the engine's `MIN_POOL` and there is one of them.* The client had its own copy of the number 20.
6. *The scope module holds no state.* The first version kept the pool in a module-level variable, so one caller's pool could be measured against another's.
7. *A link is checked before it is used.* A payload that is not a usable scope decodes to null, and the recipient is offered the vibes.
8. *A room keeps the name of the vibe it is playing.* A crafted scope has no preset id to look a name up from, so the room was given the name — a column and a function parameter.

### 5g. What the scope builder has not proved

- **The hosted Edge Runtime path still has never run.** The local one cannot boot on this host, so the Deno entry points have never been executed — only the shared handlers they call, under Node.
- **A share link is long**: about 120 characters of base64url. If that turns out to be too long in practice, the fix is a server-stored scope id, not a shorter encoding.
- **The link's payload is not signed.** Anyone can craft a link, and the server validates what it carries. A link cannot make the server do anything a player could not already do by typing the clauses into a room.
- **The registry knows one tournament** (wc-2022) while the players reference five. The tournament move lists what the registry knows, so it grows when the data does — but a player in the 2006 World Cup cannot pick it yet. That is a data gap, not a code one.

## 6. What to do next

**Phases 4 and 5 are done.** The room is on master (`docs/MULTIPLAYER.md` says how to run
it), and the scope builder is on master too (`docs/SCOPES.md` says how a vibe is stored,
shared and played). The v1 game's three pillars — a vibe you craft, a quiz the engine
writes around it, and a room of people playing it on one clock — are all built.

**Phase 6 — polish — is done.** The game has a voice, a little movement, plain words for
the times something goes wrong, and an icon for the home screen. `docs/POLISH.md` says how
it all works.

What is left:

1. **Phase 7 — the v1.1 templates.** `stat_value` and `membership` join `identify` in the
   template registry. Each is a new generator and a new option renderer; the ladder, the
   scoring and the room are untouched.
2. **The hosted project.** The code is written for it and the migrations push to it, but
   it has never been deployed. Everything here ran against the local stack.
3. **The Phase 0 falsification test.** Still not run. The game is playable today, solo or
   in a room, so it can be run with a group of friends before anything else is built on
   top of it. It is the cheapest thing on this list and the most likely to change the
   product.

Two rules carried over from the engine phase, because both were found the hard way:
**every metric states its window**, and **no player-facing string names a scope, a
predicate, a metric or a raw id**. The player-facing noun is "vibe"; the verb is "craft".
